## 一、简历项目描述（4-5行 STAR）

> **基于 FreeRTOS 的多任务智能传感器数据采集与处理系统**
>
> - 在 FreeRTOS 上设计并实现 **6 任务并发系统**，模拟加速度计(3轴/20Hz)、温度(10Hz)、光照(5Hz)三类传感器数据采集，通过**队列**实现生产者-消费者模式的任务间通信，使用**互斥锁**保护共享配置的线程安全
> - 实现**滑动窗口移动平均滤波算法**(窗口=5)和基于 **3σ 准则的实时异常检测**，支持运行时动态调参（命令行切换传感器、调整阈值）
> - 构建**运行时系统监控模块**，实时统计各任务 CPU 占用率、队列深度、采样数/异常率等关键指标
> - 在 **Windows 模拟器**上完整验证后，移植至 **STM32F103** 真实硬件运行 FreeRTOS 内核，对比验证任务调度行为

## 二、面试官追问 Q&A

### Q1：系统架构是怎样的？数据怎么流动的？

**答**：6 个 FreeRTOS 任务，分四层：
- **采集层**：3 个传感器任务 (Accel/Temp/Light)，各自按固定周期产生模拟数据，通过独立队列发送
- **处理层**：1 个 DataProcessor，while 循环逐队排空三个传感器队列，做 5 点移动平均滤波 + 3σ 异常判定
- **展示层**：1 个 Monitor，每秒通过 vTaskList 读取系统状态，打印队列深度、采样数、异常率
- **控制层**：1 个 Command，_kbhit 非阻塞轮询键盘输入，通过互斥锁修改全局配置

数据流：Sensor → Queue → Processor(滤波+异常检测) → Queue → Monitor(展示)

### Q2：为什么用队列而不是全局变量？

队列是 FreeRTOS 原生 IPC，自动处理线程安全问题，不需要自己加锁。关键是支持**阻塞等待**——生产者满时 `xQueueSend(..., 0)` 直接丢弃（避免拖慢实时采集），消费者空时可以阻塞等待。而且队列天然解耦了生产者和消费者的**速度差异**——这里加速度计 20Hz 产出、Monitor 1Hz 消费，中间队列做缓冲。

### Q3：5 点移动平均滤波器的原理？为什么窗口选5？

每个传感器维护一个长度为 5 的 FIFO 环形缓冲区。每次新数据到来，覆盖最旧的值，对窗口内 5 个值求算术平均。目的是**抑制高频噪声**（传感器模拟时加了 ±0.15g 随机噪声）。

窗口选 5 是权衡：太小（如 3）噪声抑制不够，太大（如 10）响应延迟过高。加速度计 50ms 采样周期 × 5 = 250ms 响应延迟，对大多数 IoT/可穿戴场景可接受。

### Q4：异常检测是怎么做的？3σ 准则为什么合理？

对滤波后的数据计算当前窗口的标准差。如果**原始值偏离滤波均值超过阈值×标准差**，标记为异常。

`|raw - mean| > threshold × std_dev`

3σ 准则基于正态分布假设——99.7% 数据落在 3σ 内，超出大概率是真异常。实际阈值可通过命令行动态调整（`threshold 2.0` 更敏感，`threshold 5.0` 更保守）。

### Q5：mutex 保护的粒度怎么设计的？

只在读/写全局配置 `g_config` 时持有 mutex，**临界区极短**（几个赋值语句），不会造成长时间阻塞。传感器任务每个周期先 `Take` 检查 `sensor_mask` 是否启用 → 立即 `Give` → 然后才做耗时操作（数据产生+发送），不持锁做 I/O。

### Q6：Sensor 队列满了怎么办？

`xQueueSend(..., 0)` 使用 0 超时，队列满时直接返回 `errQUEUE_FULL`。这是有意为之——**丢弃旧数据比阻塞传感器任务更合理**。实时系统中传感器数据有时效性，旧的没意义。

### Q7：64KB heap 够用吗？

6 个任务（栈：256-512 words ≈ 1-2KB each），3 个 32 深度队列（约 3KB），一个 64 深度的处理后队列（约 1.5KB），configMutex + 内核开销。总计约 20KB，64KB heap 绰绰有余。用的是 heap_4 算法（最佳适应 + 相邻空闲块合并），碎片化控制好。

### Q8：Windows 模拟器和 STM32 真机的区别？

| | Windows 模拟器 | STM32F103 |
|---|---|---|
| 调度时机 | Windows 线程调度 | 硬件 SysTick 中断 |
| 定时精度 | ms 级 (multimedia timer) | μs 级 |
| 内存模型 | 虚拟内存，栈自动增长 | 物理内存，栈固定配置 |
| 优先级数量 | 7 级 | 同 7 级 |
| 抢占行为 | 近似，非严格实时 | 严格实时抢占 |

面试官如果追问 STM32 移植细节：用 Keil + HAL 库初始化 SysTick 作为 RTOS 心跳，FreeRTOSConfig.h 中 `configCPU_CLOCK_HZ` 改为 72MHz，`configTICK_RATE_HZ` 保持 1000Hz，传感器数据用 `rand()` 替代真实 ADC 读取。

### Q9：如果让你加一个新传感器，怎么做？

1. 定义新的 SensorType 枚举值
2. 创建新 Queue
3. 写 sensor_task 函数（copy 现有模板，改周期和数据生成逻辑）
4. 在 Processor 的 while 循环中加一个新的队列排空分支
5. main() 中 xTaskCreate 启动
6. `g_config.sensor_mask` 扩展到 4 bits

完全 OCP（开闭原则）：对扩展开放，无需修改已有传感器逻辑。

### Q10：这个项目最大的技术难点是什么？

**调试多任务并发问题**。最初 Processor 用 `else if` 链导致 Temp 和 Light 传感器饥饿（只有 Accel 数据被处理），Samp=0。定位方法：通过 Monitor 的队列深度（QA=32, QT=32, QL=32）发现数据堆积，vTaskList 显示 Proc 在运行但效率低。修复：改为三个独立 while 循环排空所有队列。

## 三、核心代码讲解要点（技术面 3-5 分钟）

### 开场（30 秒）

"这是一个基于 FreeRTOS 的 6 任务系统，模拟三类传感器数据采集、实时滤波和异常检测。代码核心在 `main.c`，大概 180 行。"

### 架构讲解（1 分钟）

- 画图：Sensor × 3 → Queue × 3 → Processor → Queue → Monitor
- "采集层三个任务各跑一个周期，通过独立队列解耦"
- "Processor 用 while 循环一次排空所有待处理数据，不饿死任何传感器"
- "Monitor 每秒调用 vTaskList 拿系统快照"

### 关键代码段（1 分钟）

**滤波**：环形缓冲区 `ha[ia] = mag; ia = (ia+1) % 5`，O(1) 更新，O(n) 计算
**异常检测**：`fabsf(raw - mean) > threshold * std_dev`
**排空队列**：`while(xQueueReceive(q, &r, 0) == pdPASS)` —— 非阻塞轮询

### 踩坑分享（1 分钟）

"最初用 `fgets` 读命令，在 Windows 模拟器上阻塞了整个调度器。改成 `_kbhit()` 非阻塞轮询后解决。面试时能讲出这个排查过程，比完美代码更有说服力。"

## 六、下一步：STM32 移植路线

模拟器已经跑通，移植到 STM32F103 的步骤：

1. **Keil 新建工程**，选 STM32F103C8，配置 RCC/HAL
2. **拷贝 FreeRTOS 内核源文件**到工程（Source/*.c + portable/RVDS/ARM_CM3/*）
3. **FreeRTOSConfig.h** 中改 `configCPU_CLOCK_HZ` = 72000000
4. **中断**：SysTick_Handler → xPortSysTickHandler，PendSV_Handler → xPortPendSVHandler，SVC_Handler → vPortSVCHandler
5. **main.c** 中删掉传感器模拟，换成 ADC 读取或固定值，printf 重定向到 USART
6. 烧录、串口助手看输出

预计工作量：2-3 小时（有江协科技 HAL 库基础的话）。
